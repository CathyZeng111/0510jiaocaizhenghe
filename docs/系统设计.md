# 系统设计

## 1. 总体架构

系统采用前后端分离架构。前端使用 Vite + React，负责教材上传、解析结果展示、层级知识图谱可视化、跨教材整合对比、教师反馈对话和 RAG 问答界面。后端使用 FastAPI，负责教材解析、单本知识图谱构建、跨教材图谱整合、知识冲突检测、RAG 索引和问答生成。数据流以统一教材结构为中心：所有上传文件先解析为 `Textbook`，再被图谱模块、整合模块和 RAG 模块复用，避免各功能重复读取原始文件。

## 2. 核心数据流

用户上传 PDF / Markdown / TXT / DOCX 后，后端解析模块逐页或逐段抽取正文，并输出 `textbook_id / filename / title / total_pages / total_chars / chapters`。知识图谱模块读取章节结构，生成 `primary / secondary / knowledge_point` 三层节点，并构造 `contains / prerequisite / parallel / applies_to` 关系。跨教材整合模块接收多本教材图谱，执行名称归一化、相似度计算、合并决策、30% 字符预算压缩和冲突检测，最终输出 `GraphIntegrationResult`。RAG 模块读取教材章节内容，按 800 字窗口、80 字重叠分块，调用 embedding 模型向量化并写入 Chroma，用户提问时检索 top-5 chunk 注入 LLM prompt 生成带引用回答。

## 3. 技术选型

后端选择 FastAPI 是因为它适合快速定义 JSON API 和文件上传接口，并且与 Python 文档解析、NLP 和向量库生态兼容。PDF 解析使用 PyMuPDF，支持逐页读取、字体信息和文本 block 处理，便于章节识别和过滤页眉页脚。DOCX 解析使用 python-docx。前端选择 React 是为了快速构建多标签工作台和交互式图谱组件。向量存储使用 Chroma，部署成本低，适合黑客松场景下的本地持久化索引。模型调用通过 ModelScope / OpenRouter 配置化接入，真实 API Key 只放在 `.env`，仓库只提交 `.env.example`。

## 4. 模块边界

`backend/app/parsers.py` 只负责教材加载与解析；`backend/app/knowledge_graph.py` 只负责单本教材图谱构建；`backend/app/graph_integration.py` 只负责跨教材节点对齐、压缩、冲突检测和教师反馈修正；`backend/app/rag.py` 只负责分块、向量化、索引、检索和回答生成。前端的 `KnowledgeGraphPanel`、`IntegrationPanel`、`RagPanel` 分别对应三个主要工作区。这样的模块边界让每个功能可单独验收，也便于后续替换某个算法，例如将本地术语抽取升级为 LLM 抽取，或将 Chroma 替换为云端向量库。

## 5. 部署设计

项目支持本地开发和 Docker 部署两种方式。本地开发时分别启动 `uvicorn backend.app.main:app --reload --port 8000` 和 `npm run dev`。Docker 部署时，根目录 `Dockerfile` 构建后端镜像，`frontend/Dockerfile` 使用 Node 构建前端并用 nginx 在 5173 端口托管静态资源，`docker-compose.yml` 同时启动 backend 和 frontend，后端通过 `env_file: .env` 读取模型配置。`.gitignore` 明确排除教材 PDF、`textbooks/`、Chroma 数据库、`.env`、构建产物和本地缓存，保证 GitHub 仓库只包含源代码、文档、配置模板和可复现报告。
